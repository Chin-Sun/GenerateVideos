# 借鉴开源项目，构建飞书中文对白短剧机器人

**没有一个本次核验的项目，已被证明能够直接完成“飞书输入提示词 → PPAPI MiniMax-H3 → 约 60 秒多镜头中文角色对白与同步口型 → 保存工程 → 对话局部修改 → 云端长期恢复运行”的全部闭环。**但已有足够的可借鉴组件：LocalMiniDrama 最贴近可编辑短剧工程，Jellyfish 提供后台制作状态设计，MuseBot 有真实飞书视频投递代码，MuseTalk 等补足音频驱动口型。推荐采用“小型自有工程控制层＋现成 SDK／渲染组件＋按镜头选择生成路线”，而不是把旁白视频工具改名为对白短剧系统。H3 原生中文对白应先试验，不能把音色参考理解为逐字台词和说话者绑定保证；若不能通过验收，则锁定中文 TTS／演员音轨，再做口型处理。**因此，“云服务器不需要 GPU”只能在全部推理由外部托管服务完成时成立；自托管口型模型需要独立、可按需启停的 GPU worker。**本报告整理了 **34 个去重候选条目**，其中包含家族或明确配套组合；它不是 34 个端到端产品，也不是截至调研日的全网穷尽名单。

本文面向准备建设个人飞书视频机器人的开发者，目标是决定借什么、自己做什么、先验证什么，而不是提供未经试运行的部署承诺。研究快照日期为 **2026 年 11 月 17 日**；未部署、未生成视频、未调用付费模型，也未授权支出。预算尚未设置，**不等于预算无限**。

## 确定证据边界，避免把功能声明当成验收

本节帮助读者判断下文每项结论能支持什么决策。报告仅综合三份研究笔记：[流水线调研](</Users/sunqian/Desktop/Projects/Demo/GenerateVideos/research_notes/飞书 中文剧情视频 开源项目调研/pipelines.md>)、[口型模型调研](</Users/sunqian/Desktop/Projects/Demo/GenerateVideos/research_notes/飞书 中文剧情视频 开源项目调研/lipsync.md>)和[基础设施调研](</Users/sunqian/Desktop/Projects/Demo/GenerateVideos/research_notes/飞书 中文剧情视频 开源项目调研/infrastructure.md>)，没有更早研究作为输入，也没有在撰写阶段重新进行广泛检索。链接中的上游 README、源码、模型卡和许可证是主要证据；本文的架构和验收方案是工程建议，不能反向理解为某个仓库已经实现。

原研究覆盖 GitHub 仓库检索、仓库元数据、公开 README、少量关键源码、许可证、Hugging Face 官方模型卡和 PPAPI 文档。检索主题包括 `AI short drama storyboard`、`AI video director`、`AI 短剧`、NarratoAI、MoneyPrinterTurbo，以及飞书视频机器人、对话编辑、异步恢复、中文口型和多人音频驱动等方向。通用搜索服务返回 `401`，GitHub 未认证 API 后期返回 `403` 限流，研究者停止扩搜，没有绕过限制；口型部分还直接读取官方仓库和模型卡。这些限制会漏掉新项目、小型插件、私有实现和没有被关键词命中的仓库，所以结论是“本次未核验到完整成品”，不是“世界上不存在”。

## 选择双路线验证中文对白，而非用旁白替代

本节明确最关键的模型决策：**“有音频”“有 dialogue 字段”“能 TTS 配音”都不足以满足角色说中文且嘴部同步。**合格镜头必须能回答谁在说、说了什么、可见嘴部是否与声音匹配、静默角色是否乱动嘴；整片加解说音轨不算通过。合理使用反应镜头或角色画外对白是剪辑手法，但不能把所有对白都藏到画外来规避口型要求。

PPAPI 当前 H3 文档使用 `MiniMax-H3` 和 `POST /v2/video_generation`，异步读取 `task.status`、`task.content.url`，单次时长为 **4～15 秒**，而不是 60 秒。文档支持 768P／2K、多模态参考，最多 9 张图、3 段视频、3 段音频；参考音视频各单段 2～15 秒，每类总长度最多 15 秒。**首尾帧角色与 `reference_*` 模式不能混合**，因此不能设计同时依赖首尾帧锁构图和音频参考的同一个请求。([PPAPI H3 文档](<https://pp-api.docs.buildwithfern.com/docs/advanced/video-generation/mini-max-h-3.md>))

`reference_audio` 的官方示例说使用参考声音的音色，而没有承诺原音轨逐采样保留、按给定文本逐字发声、音素时间对齐或多人脸与声线绑定。这不证明 H3 一定做不到中文对白，只证明**不能在试验前把它当作已解决问题**。AICG3D 的声线座位和 `<d>` 标签适合借作内部对白表达，但不是 PPAPI 的已支持参数，不能直接塞入请求并声称生效。([H3 文档](<https://pp-api.docs.buildwithfern.com/docs/advanced/video-generation/mini-max-h-3.md>))([AICG3D README](<https://github.com/JGRFW/comfyui-AICG3D/blob/main/README.md>))

| 路线 | 具体流程 | 采用条件与代价 |
|---|---|---|
| **A：H3 原生对白优先试验** | 固定角色参考与中文逐字台词 → 按供应商支持字段提交 → 保存原始音视频 → 逐镜验收 → 保留对白拼接 | 如果准确台词、口型、说话者和身份全部通过，可省后处理；任何一项未达标不能靠旁白补齐。参考音色不等于锁音轨 |
| **B：锁定音轨＋口型处理** | 合法中文 TTS／演员录音 → 人工确认台词、声线和停顿 → H3 底片 → MuseTalk 或 LatentSync → 验收 → 使用锁定原音轨合成 | 锁音轨保证最终听到的台词来源可控，但不自动保证嘴形正确；增加推理、依赖许可与视觉损伤风险。自托管需 GPU，托管则另核价格与隐私 |
| **C：特定镜头音频驱动生成** | 参考图＋分角色音轨＋动作提示 → MultiTalk／LongCat；或 H3 底片＋InfiniteTalk | 仅作双人同框或身体动作的探索支线，不能先承诺任意遮挡、同时说话和跨镜头一致。若替代 H3 生成主体镜头，应向用户明确，不冒称全部由 H3 生成 |

约 60 秒应先按剧情规划约 6～12 个可替换短镜头，具体数量由台词时长、H3 限制和剪辑节奏决定；这是设计建议，不是模型最优参数。第一版优先单人中近景和双人轮流说话，暂不把奔跑、手遮嘴、强侧脸、重叠对白同时设为成功前提。LongCat 支持多音频组合，MultiTalk 支持多路音频，但说话者时轴、静默轨和角色引用仍应由工程层管理。([LongCat README](<https://github.com/meituan-longcat/LongCat-Video/blob/main/README.md>))([MultiTalk README](<https://github.com/MeiGen-AI/MultiTalk/blob/main/README.md>))

视觉一致性也不能只检查生成前的参考图。MuseTalk 文档明确提到胡须、唇形、唇色与抖动等限制，InfiniteTalk 会联动头部和身体；后处理可能破坏 H3 已生成的身份或动作。因此应保存处理前后版本并对比，不能把“口型工具”理解为无损覆盖层。([MuseTalk 限制](<https://github.com/TMElyralab/MuseTalk#limitations>))([InfiniteTalk 特性](<https://github.com/MeiGen-AI/InfiniteTalk#-key-features>))

## 构建可恢复的云端架构，把工程与聊天分开

本节提供修订后的部署设计与复用边界。推荐云端常驻的是 **CPU 控制平面、数据库和私有存储**；生成、口型与合成在独立 worker 执行。全部推理使用经授权的外部 API 时，控制服务器本身无需 GPU；采用开源口型权重自托管时，则接独立按需 GPU worker。不要为了“最初说不需要 GPU”而把真正对白要求退化为配音，也不要因此默认购买常驻高规格 GPU。

```text
飞书用户／交互卡片
    │  身份白名单、事件去重、快速确认
    ▼
CPU 控制平面：意图解析、工程选择、修改预览、预算确认
    │
    ├── PostgreSQL：工程版本、镜头、任务、提交记录、投递 outbox
    ├── 私有对象存储：参考图、锁定音轨、原始片段、时间线、成片
    │
    ▼
持久调度器：数据库租约／任务队列、重试、轮询、恢复
    ├── PPAPI H3 adapter：提交、保存任务 ID、轮询、下载
    ├── 可选推理 worker：托管口型 API 或按需 GPU 模型服务
    └── CPU render worker：FFmpeg／MoviePy，必要时 Remotion
    │
    ▼
逐镜质量门 → 固定版本渲染 → 飞书上传／发送 → 投递记录
```

这张图是推荐架构，不是已经部署的系统。首版可在一个小型云环境中分进程／容器运行 bot、调度和 CPU 合成，但数据库、持久卷、对象存储与备份必须有明确边界；具体机器规格不能在未测分辨率、并发、编解码与资源占用前凭空给出。素材存储保持私有，预览使用短期授权 URL；外部 GPU worker 仅获得任务所需对象访问权，禁止把存储和 PPAPI 主密钥写入提示词或发回飞书。

### 保存语义工程与剪辑时间线，不把 MP4 当成工程

工程至少需要 `Project`、`ProjectVersion`、`Character`、`Shot`、`Asset/Take`、`Timeline`、`Render`、`Job` 和 `Delivery`。其中版本记录父版本、修改原文与解析 patch；镜头保留稳定 `shot_id`、说话人、逐字中文、起止时间、机位、服装、道具、参考资产哈希和选中的 take；资产保留原始输出、音轨、校验和、供应商任务 ID、模型版本及授权来源；渲染记录精确源版本和输出哈希。临时 provider URL 不是永久资产地址，聊天历史也不是工程事实源。

例如，用户说“基于 v3，把第 4 镜乙的最后一句改成‘明天上午九点见’，其他不动”。系统先解析为针对 v3 的 patch，展示要重做的音轨、口型或镜头及预估费用，再确认生成 v4；没有影响的镜头继续引用原文件，v3 不被覆盖。只改字幕、片头、配乐或顺序通常只需重渲染；改对白、表演和人物外观往往需要重生相关镜头，跨镜头服装／道具变化可能扩大失效范围，不能静默全部重做。

OTIO 可以保存剪辑关系和外部引用，Remotion 可以保存 composition 与 props，MoviePy 可以保存合成配方，但它们均不能从任意成片自动还原剧本、人物提示词和生成依赖。因此导出包应包含工程清单、时间线、可访问素材和版本说明，而不只是 MP4 或指向临时地址的 JSON；具体 NLE 导出特效保真需单独测。([OTIO README](<https://github.com/AcademySoftwareFoundation/OpenTimelineIO/blob/main/README.md>))([Remotion README](<https://github.com/remotion-dev/remotion/blob/main/README.md>))

### 持久化每次外部操作，避免重启重扣费和投递错人

官方 Node SDK 文档要求事件处理及时完成，长连接收到消息后应在约 3 秒内处理，否则可能重推；因此飞书入口只做验证、去重、落库与快速确认，不等待完整视频生成。卡片长连接回调在不同文档段落中有差异，部署时固定 SDK 版本验证，不能承诺任意版本均支持。([Node SDK README](<https://github.com/larksuite/node-sdk/blob/main/README.md>))

推荐状态机如下；状态名是内部设计，不冒充 PPAPI 原生字段。

```text
queued → submitting → generating → downloading
       → assets_ready → rendering → delivering → succeeded
异常分支：retry_wait / failed / cancel_requested / unknown_submission
```

每步保存租约、心跳、尝试次数、错误分类和下次轮询时间。提交前记录意图，成功后保存 `provider_task_id`；重启先查询已知任务，而不是重新生成。若提交超时但供应商可能已经受理，应进入 `unknown_submission` 对账或人工确认，不能盲目重发；PPAPI 的幂等键、按请求 ID 查询、取消、回调、结果保留期与 SLA 尚未核实，不能自造保证。Temporal 能帮助恢复工作流，但同样不能代替外部供应商的幂等契约。([Temporal Activities](<https://docs.temporal.io/activities>))

投递使用独立 outbox，保存固定 `tenant_id`、`chat_id`、触发消息、版本、上传后的 `file_key` 和发送结果。上传成功而发送失败时只重投递，不重生成；若发送结果本身不确定，先核当前飞书去重契约再决定重发，不能承诺绝对 exactly-once。对象存储和数据库做备份并演练恢复，生成中间资产按明确策略保留；用户修改旧工程时若原素材已删除，应明确告知，而不是假装仍可无损编辑。

## 执行分阶段验证，用硬验收决定是否继续投入

本节给出最小验证方案，**以下都是拟定测试，不是已完成成绩**。先确认一个小额、有限次数的 PoC 预算、单次重试上限、日／月封顶和失败停止条件，再授权真实调用。未设置金额前只可进行不收费的代码与 mock 验证；云资源、托管推理、存储和外网流量都不能被默认为免费。

| 阶段 | 测什么、为什么 | 最小动作与观察字段 | 成功标志与失败后的决定 |
|---|---|---|---|
| **P0：锁定契约与授权** | 避免用错 H3 接口、复制受限权重或误开支出 | 固定仓库 commit／模型版本；核 PPAPI 参数和任务返回；核飞书应用、权限、媒体限制；列代码／主权重／依赖／声音授权清单；用 mock 测状态机 | 缺失许可、费用或权限明确列阻塞项；没有预算确认不发付费请求，不部署云 GPU |
| **P1：验证 3 个短镜的真实中文对白** | 判断 H3 原生路线是否成立 | 固定甲乙两角色，甲说、乙说、甲再说；包含数字、人名、停顿，使用同一参考资产；保存请求、原始输出、ASR 与人工复核；原生不合格时，经确认测试锁轨＋MuseTalk，LatentSync 作对照 | 每条批准台词完整准确，无额外旁白、漏词、串人；可见说话者正确，音色连续。听懂大意但改词不算通过 |
| **P2：验证嘴部与身份，再拼约 60 秒** | 防止“声音正确、嘴错了”以及后处理换脸 | 检查闭唇／爆破音、静音嘴动、音画偏移；对比正脸、三分之二角度及一个困难镜头；核头发、脸、服装和道具；扩为约 6～12 镜并记录实际片长 | 人工逐镜确认无明显错位、错误说话者或身份漂移；嘴被遮挡的镜头不能独自充当口型通过证据。约 60 秒容差由用户先确认；不拉伸台词强凑时长 |
| **P3：验证持久任务与飞书投递** | 防止崩溃丢任务、重复扣费、串聊 | 在已取得任务 ID、下载中、上传成功发送前分别重启 worker；重放同一飞书事件；两会话交错发任务；观察任务、提交、资产、outbox 与收件人记录 | 事件不重复建业务任务；已提交任务恢复查询；不确定提交转对账，不盲重发；只恢复失败阶段；视频发到固定目标。平台侧去重不足之处如实记录 |
| **P4：验证局部版本编辑与工程可用性** | 证明交付的是工程，不只是一次性 MP4 | 完成 v1 后只改第 2 镜一句话；生成 v2；对比未改镜头 hash；打开旧版、导出工程并重新渲染；模拟并发修改同一父版本 | 旧版不被覆盖，未改镜头 hash 不变，受影响资产可追溯；新旧版均可打开；并发冲突提示而非静默覆盖；导出素材可访问 |
| **P5：决定是否扩多人／高动作与长期运行** | 避免在基础失败时继续堆模型和成本 | 经单独授权再测 MultiTalk／LongCat／InfiniteTalk；记录 GPU 峰值、实际耗时、重试、费用、动作与身份变化；演练数据库／对象存储恢复 | 只保留通过本剧本需求的模型；无法过关就限制景别或继续研发，不承诺任意人物／场景。确认真实费用和保留策略后再批准常驻服务 |

台词验收以批准文本为基准，ASR 字符错误率只是辅助；中文同音字、人名和数字需要人工听审，不能让 ASR 错误反过来误判音频。口型可记录音画偏移和同步指标，但不在没有校准测试集时编造通用分数门槛；首个验收应由人工逐镜检查闭唇、发声起止、静音和人物对应。身份评审同时看前后处理、跨镜头变化，不只看某一张静帧。

还需由用户在实施前确定画风、角色数量、是否商业发行及地区、可接受的中近景比例、是否允许第三方托管音视频、素材保留期限和可支出预算。这些信息会改变许可证选择、镜头设计和部署形态，但不妨碍当前结论：先用最小三镜证明对白，再验证工程修改和重启恢复，最后才扩大到常驻生产。

## 形成实施结论，先证明对白再扩大自动化

最值得投资的自有资产不是另一套文生视频界面，而是**可追溯的角色／台词／镜头版本模型，以及将外部生成结果转化为可验收工程的控制层**。模型会更新、平台会换接口，只要原始素材、锁定音轨、生成契约、版本依赖和验收记录由自己掌握，就能替换 H3 provider 或口型 worker，而不必重建整个用户工作流。

近期推荐组合是官方飞书 SDK 与 MuseBot 投递参考、LocalMiniDrama／Jellyfish 的工程与状态设计、PPAPI H3 独立适配、MuseTalk 的受控口型基线及 MoviePy／FFmpeg 合成；LatentSync 先过权重授权检查，LongCat／MultiTalk 保留为多人探索支线。**只有先证明“角色确实按指定中文说话，嘴也对应得上”，才有理由投入更多云资源；只有再证明“重启不丢、修订不覆盖、投递不串人”，才有理由称它为长期运行的视频机器人。**本报告完成的是选型与验证设计，不构成部署、付费、性能或成片质量承诺。
